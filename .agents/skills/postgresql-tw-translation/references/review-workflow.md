# Revision re-review and user rulings

Read this reference for revised submissions, repeated rejections, or a proposed partial re-review. It does not replace the project's collaboration protocol or authorize publication.

## Establish the reviewed versions

- Identify the page and exact revised content, its previous submission, the version-pinned official source or saved source snapshot, and the applicable review rules. Use content hashes and saved results where available; do not rely only on a progress board or a description such as "latest revision."
- Read all available same-page rejection reasons and relevant user rulings before resubmitting. Keep historical submissions and rejection evidence intact.
- Treat findings as claims to verify against the actual source and translation. A prior rejection is not automatically correct, and a revised sentence is not automatically correct merely because it follows that rejection.
- Before resubmission, check whether the publisher has already applied an equivalent fix or published a later accepted version. Compare the exact published/submitted content and scope; matching the one corrected sentence alone does not prove that the whole revision is redundant. Explain any normalization used, and do not blindly ignore dates or other metadata.
- Do not resubmit a duplicate or overwrite a newer accepted page with an older rejected draft. Preserve redundant submissions intact and use the project's authorized withdrawal/archive procedure if needed; do not delete history or move another agent's files without authority. Base a genuine revision on the latest relevant version after reconciling publisher changes.
- Re-run applicable deterministic checks and refresh submission hashes/timestamps. Update source-verification dates only after actually rechecking the source, not merely because the revision is being sent again.

## Resolve repeated or conflicting findings

- If the same issue is rejected again, compare the actual passages and the earlier reasons before taking further action. Check whether the reviewer missed existing content, repeated a disproven claim, or contradicted a user ruling.
- Check the actual reviewer input before accepting a "missing content" finding. Long single-line tables can exceed excerpt or input limits even when all rows exist in the file. Verify row IDs, order, cell contents, and complete input coverage; provide exact locations. Row-per-line formatting can improve inspection, but is not proof that truncation or omission has been eliminated.
- When changing packet layout or splitting a table for review, prove complete, nonduplicated coverage and reconstructability of protected content. Do not add duplicate rows to satisfy a disproven rejection or substitute a diagnostic excerpt for full required evidence. If a finding may concern a conversion artifact rather than official text, consult the source-validation reference before adding an erratum.
- When an issue repeats, reasons conflict, or a semantic request conflicts with structural preservation, present the official passage, the relevant translation or structural evidence, the historical reasons, and a concrete recommendation for user adjudication. Do not autonomously re-submit the same disputed issue in a loop.
- A user ruling resolves only its stated issue and scope. It is not whole-page approval and does not waive review of other content. Do not re-reject the accepted handling on the same grounds.
- Keep individual rulings in the project's designated protocol or decision record, not copied into this skill. Consult that authoritative record for the current decision. Update it only within the user's authorization.

## Preserve source code when correcting documentation

- Preserve original code byte-for-byte within the project's agreed newline/encoding convention, including syntax mistakes, comments, punctuation, and English strings. Do not insert a translator's note into protected code.
- For a verified source defect, place a Traditional Chinese translator's note outside the code block explaining the original spelling, the problem, and the supported correction. Preserve uncertainty when the evidence is incomplete; ask for a decision when necessary.
- When preserved source code already has an accurate, accepted note, do not require changing that code as a condition of approval. Other issues in the page still require review.
- If a valid follow-up finding narrows an existing note, change only the supported scope while keeping the accurate disclosure of the source defect. If the alleged defect was disproven, correct or remove the misleading note within the authorized scope rather than preserving a false claim for historical consistency.

## Decide whether partial re-review is valid

- A changed-section packet is not a substitute for the first complete semantic review. Account for every changed span, including moved content and newly affected context; preserve the source's conditions, exceptions, and cross-references.
- Exclude unchanged content only when it has valid prior review coverage compatible with the current source, content, and applicable rules. A page's previous review attempt or the absence of a previous complaint does not by itself prove that coverage.
- If the source, rules, or relevant content changes, reassess whether prior coverage and cached results remain valid. Do not silently reuse incompatible approvals; invalidate or expand the affected review as needed.
- If alignment or coverage cannot be established, fall back to the full affected sections, or the whole page when necessary. Do not omit unresolved changes, truncate evidence, or treat alignment success as semantic approval.
- Report separately what was reviewed now, what valid coverage was reused, what remains unresolved, and whether the result is a review finding or an authorized publication outcome.
